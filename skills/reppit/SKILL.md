# RePPIT 工作流

处理"需求清楚但代码库不清楚"的任务。核心是**先分阶段产出文件，再动手写代码**，并在三个人工检查点停下来等用户确认。

```
Research ──► Propose ──► Plan ──► Implement ──► Test
 research.md  proposal.md  plan.md   代码+进度    测试证据
    ▲                                              │
    └──────── 测试暴露理解错误时回到调研 ◄──────────┘
```

## 何时用 / 何时不用

用：陌生代码库、跨模块或跨前后端的改动、需要先定位数据流再决定方案、改动会影响多个文件。

不用（会变成纯负担）：单文件小修、明确的语法/拼写错误、用户已给出精确改法的任务、纯问答。

调研后才发现是简单任务：在 Research 检查点申请降级，不必硬走完 Propose/Plan，见「降级通道」。

## 产出物位置

默认 `docs/reppit/<feature-slug>/`，包含 `research.md`、`proposal.md`、`plan.md`；测试证据追加在 plan.md 的「最终验证证据」区块。
若仓库已有 `docs/research/`、`docs/plans/` 等约定，跟随仓库约定。

**模板先行**：产出任一文件前，先读取本技能 `assets/` 下对应模板（`research.md` / `proposal.md` / `plan.md`），沿用其小节标题与结构，不要凭记忆自造标题。

**Git 生命周期**：默认按"临时草稿"处理；开始 Research 时顺带用一句话告知用户产物路径与默认策略即可，**不要为此停下等回复**。用户想改成下面另外两种时，再一句话确认后切换：

- **临时草稿**（默认）：不提交，Test 通过后由用户决定保留还是清理；清理前必须得到用户确认。
- **提交留档**：用户要求留档时，随业务 PR 提交，作为决策记录。
- **本地忽略**：用户要求时，把 `docs/reppit/` 或本次 feature 目录写进 `.git/info/exclude`（只影响本机，不修改仓库 `.gitignore`）。

提交业务改动前先看 `git status`，不要用 `git add .` 把过程文档混进业务提交。

## 硬规则（必须遵守）

1. **Research 阶段禁止任何修改**：不写业务代码、不改配置，只用读/搜索/运行只读命令。发现"顺手就能修"的问题，记进 research.md 的"未确认事项 / 风险"一节，不要动手。**产出 research.md 后必须停下**，等用户确认调研事实无误再进入 Propose；用户也可在此检查点明确同意走「降级通道」。
2. **Propose 阶段必须给 2~3 个方案并停下**。即使某一方案明显更好，也要给出被淘汰方案的对比。proposal.md 必须写清"明确不做（Non-Goals）"。除非用户明确说"你自己选"或已批准「降级通道」，否则不得进入 Plan/Implement。
3. **Plan 阶段必须停下等确认**。计划的杠杆比代码大，用户不点头不写代码。只有用户明确同意同时跳过 Plan（见「降级通道」）时，才能直接进入 Implement。
4. **Implement 一次只做一个阶段**，做完立刻跑该阶段写明的验证，再回写 plan.md（勾掉复选框 + 记录偏差）。验证没过不得进入下一阶段。不越出 plan.md 的 Non-Goals。
5. **Test 靠证据，不靠声明**。禁止用"应该可以了""理论上没问题"结尾；必须给出实际执行的命令与输出摘要。UI 改动要真的打开页面看一眼。证据必须落盘到 plan.md 的「最终验证证据」区块（命令 + 结果 + 未覆盖项），不能只留在对话里。
6. **测试暴露的是理解错误就回到 Research**，不要在实现层打补丁。返工次数受 #8 熔断限制。
7. **上下文将满时**：先把当前阶段状态、未决问题、下一步写进 plan.md 的「交接与阻塞信息」区块，再提示用户开新会话从文件继续，不要靠对话历史延续。
8. **失败熔断**：同一阶段的验证连续失败 3 次，或 Research 返工累计 2 次，必须停下。把阻塞点、已尝试的做法、实际报错写进 plan.md 的「交接与阻塞信息」区块，请用户介入；禁止无限重试或换着花样硬试。

## 降级通道（简单任务）

RePPIT 处理的是"需求清楚但代码库不清楚"的任务。若 Research 后发现任务其实很简单，允许在 Research 检查点申请降级，避免为了流程而流程。

**申请条件（同时满足才可提）**：

- 改动面集中在 1~2 个文件；
- 实现路线唯一，没有需要用户选型的取舍（典型：已定位到明确根因的 Bug）；
- 不涉及接口、数据结构、依赖或架构变更。

**申请方式**：在汇报 research.md 时用一句话主动提议，例如"方案唯一，建议跳过 Propose 直接进入 Plan"或"改动只有一处，建议跳过 Propose 和 Plan 直接 Implement"。由用户一句话拍板；用户未明确同意时，仍走完整流程。

**批准后**：

- 只跳过 Propose：直接写 plan.md，Plan 检查点仍要停下等确认。
- Propose 和 Plan 都跳过：先补一份最小 plan.md（改动文件、做法、验证命令），再进入 Implement；「最终验证证据」仍必须落盘。
- 把降级决定与理由记进 plan.md 的「偏差记录」，便于复盘。

## 断点续跑与跨会话接力

开始任何阶段前，先检查目标目录是否已有产物，按已有文件恢复状态：

- **已有 plan.md**：依次读 `plan.md` → `proposal.md` → `research.md`，优先按「交接与阻塞信息」的"下一步"直接续跑。已勾选的阶段不得重做；尚未确认的检查点仍要停下等确认。
- **只有 research.md / proposal.md**：从对应检查点继续（补确认或进入下一阶段），不要重跑已完成阶段。
- **目录不存在或为空**：按正常流程从 Research 开始。
- 开新会话或换 Agent 客户端时同样适用；文件是唯一状态源，对话历史不算。

## 各阶段要点

### Research — 只描述现状
回答四类问题：数据从哪来 → 存在哪 → 在哪渲染/使用 → 有哪些约定（测试怎么跑、风格、已有可复用组件）。

研究问题要具体到可验证，例如"交易数据的模型定义在哪、类别字段怎么存""前端图表用什么库、在哪些组件""后端有没有按时间聚合的接口""测试怎么跑"。

产出 `assets/research.md` 模板：结论摘要 + 关键文件路径与行号 + 数据流 + 可复用组件 + 测试方式 + 未确认事项。
**人工检查点**：让用户确认没找错对象（比如是否找对了交易数据的表）。确认后才进入 Propose；若符合「降级通道」条件，可在此一并提议跳过后续阶段。

### Propose — 2~3 条路线对比
每条写：做法、改动范围（文件/模块）、优点、缺点、风险。最后给出推荐及理由，但选择权交给用户。
每个方案都要写明明确不做（Non-Goals），挡住后续范围扩张。
注意覆盖不同**层次**的方案（纯前端、前后端配合、数据层/运维），否则对比没有信息量。
产出 `assets/proposal.md` 模板。

### Plan — 傻瓜也能执行的步骤
按模块或垂直切片拆 Phase（后端、前端、CLI、库内部模块都行，不限于前后端），每步必须写：**改哪个文件、改什么、怎么验证**。验证写成可执行命令或明确的手工观察点。
产出 `assets/plan.md` 模板（带复选框任务清单、Non-Goals、最终验证证据区块）。

### Implement — 按阶段执行
只做当前阶段；不顺手重构、不扩范围。需要偏离计划时，先在 plan.md 记录偏离原因再继续。

### Test — 证据胜于声明
跑自动化测试、类型检查、lint（命令从仓库 README/package.json/Makefile 里查，不要凭空假设）。报告格式：命令 + 结果 + 未覆盖的部分。同时把证据写进 plan.md 的「最终验证证据」区块，对话里只回摘要和文件路径。

## 可选子技能（已安装才用，未装则按本文件规则手动执行）

RePPIT 是主骨架，以下技能只作为某一步的加强，不替代阶段划分，也不复述其内容：

| 时机 | 子技能 | 作用 |
| --- | --- | --- |
| 需求没问清、边界含糊 | `grilling` / `grill-me` | 按设计树分轮追问，每问附推荐答案（Research 后、Propose 前） |
| 写代码阶段 | `tdd` | 红-绿-重构，一次一个垂直切片（Implement 内） |
| 测试反复变红且原因不明 | `diagnosing-bugs` | 先造能变红的反馈回路，再最小化→假设→埋点→修→回归 |
| 提交前 | `code-review` | Standards 与 Spec 两轴审查 diff |
| 上下文将满 | `handoff` | 生成交接文档，可替代手写的「交接与阻塞信息」 |

这些技能与本流程冲突时，以本文件的硬规则为准（如子技能想越过"调研必停/方案必停/计划必停"，一律不越）。

## 汇报格式

每阶段结束时用简短结构回复：产出文件路径、关键结论、下一步需要用户做什么（选方案 / 确认计划 / 提供信息）。不要复述整个文件内容。

需要用户决策时，当前工具若提供提问工具（如 AskUserQuestion / question）就用它提问；否则在回复末尾直接列出 1~3 个待确认问题，然后停下。
