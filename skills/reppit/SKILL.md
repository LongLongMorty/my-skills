# RePPIT 工作流

处理"需求清楚但代码库不清楚"的任务。核心是**先分阶段产出文件，再动手写代码**，并在三个人工检查点停下来等用户确认。

```
Research ──► Propose ──► Plan ──► Implement ──► Test
 research.md  proposal.md  plan.md   代码+进度    测试证据
    ▲                                              │
    └──────── 测试暴露理解错误时回到调研 ◄──────────┘
```

## 何时用 / 何时不用

用：陌生代码库、跨模块或跨前后端的改动、需要先定位数据流再决定方案、改动会影响多个文件。

不用（会变成纯负担）：单文件小修、明确的语法/拼写错误、用户已给出精确改法的任务、纯问答。

## 产出物位置

默认 `docs/reppit/<feature-slug>/`，包含 `research.md`、`proposal.md`、`plan.md`。
若仓库已有 `docs/research/`、`docs/plans/` 等约定，跟随仓库约定。开始前用一句话告知用户本轮将产物写到哪里。

## 硬规则（必须遵守）

1. **Research 阶段禁止任何修改**：不写业务代码、不改配置，只用读/搜索/运行只读命令。发现"顺手就能修"的问题，记进 research.md 的"待确认"一节，不要动手。
2. **Propose 阶段必须给 2~3 个方案并停下**。即使某一方案明显更好，也要给出被淘汰方案的对比。除非用户明确说"你自己选"，否则不得进入 Plan/Implement。
3. **Plan 阶段必须停下等确认**。计划的杠杆比代码大，用户不点头不写代码。
4. **Implement 一次只做一个阶段**，做完立刻跑该阶段写明的验证，再回写 plan.md（勾掉复选框 + 记录偏差）。验证没过不得进入下一阶段。
5. **Test 靠证据，不靠声明**。禁止用"应该可以了""理论上没问题"结尾；必须给出实际执行的命令与输出摘要。UI 改动要真的打开页面看一眼。
6. **测试暴露的是理解错误就回到 Research**，不要在实现层打补丁。
7. **上下文将满时**：先把当前阶段状态、未决问题、下一步写进 plan.md，再提示用户开新会话从文件继续，不要靠对话历史延续。

## 各阶段要点

### Research — 只描述现状
回答四类问题：数据从哪来 → 存在哪 → 在哪渲染/使用 → 有哪些约定（测试怎么跑、风格、已有可复用组件）。

研究问题要具体到可验证，例如"交易数据的模型定义在哪、类别字段怎么存""前端图表用什么库、在哪些组件""后端有没有按时间聚合的接口""测试怎么跑"。

产出 `assets/research.md` 模板：结论摘要 + 关键文件路径与行号 + 数据流 + 可复用组件 + 测试方式 + 未确认事项。
**人工检查点**：让用户确认没找错对象（比如是否找对了交易数据的表）。

### Propose — 2~3 条路线对比
每条写：做法、改动范围（文件/模块）、优点、缺点、风险。最后给出推荐及理由，但选择权交给用户。
注意覆盖不同**层次**的方案（纯前端、前后端配合、数据层/运维），否则对比没有信息量。
产出 `assets/proposal.md` 模板。

### Plan — 傻瓜也能执行的步骤
按阶段拆（后端 → 前端 → 联调，或按垂直切片），每步必须写：**改哪个文件、改什么、怎么验证**。验证写成可执行命令或明确的手工观察点。
产出 `assets/plan.md` 模板（带复选框任务清单）。

### Implement — 按阶段执行
只做当前阶段；不顺手重构、不扩范围。需要偏离计划时，先在 plan.md 记录偏离原因再继续。

### Test — 证据胜于声明
跑自动化测试、类型检查、lint（命令从仓库 README/package.json/Makefile 里查，不要凭空假设）。报告格式：命令 + 结果 + 未覆盖的部分。

## 可选子技能（已安装才用，未装则按本文件规则手动执行）

RePPIT 是主骨架，以下技能只作为某一步的加强，不替代阶段划分，也不复述其内容：

| 时机 | 子技能 | 作用 |
| --- | --- | --- |
| 需求没问清、边界含糊 | `grilling` / `grill-me` | 按设计树分轮追问，每问附推荐答案（Research 后、Propose 前） |
| 写代码阶段 | `tdd` | 红-绿-重构，一次一个垂直切片（Implement 内） |
| 测试反复变红且原因不明 | `diagnosing-bugs` | 先造能变红的反馈回路，再最小化→假设→埋点→修→回归 |
| 提交前 | `code-review` | Standards 与 Spec 两轴审查 diff |
| 上下文将满 | `handoff` | 生成交接文档，替代手写的交接段 |

这些技能与本流程冲突时，以本文件的硬规则为准（如子技能想越过"方案必停/计划必停"，一律不越）。

## 汇报格式

每阶段结束时用简短结构回复：产出文件路径、关键结论、下一步需要用户做什么（选方案 / 确认计划 / 提供信息）。不要复述整个文件内容。

需要用户决策时，当前工具若提供提问工具（如 AskUserQuestion / question）就用它提问；否则在回复末尾直接列出 1~3 个待确认问题，然后停下。
